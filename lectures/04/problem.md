# تمارين وواجبات Lecture 04: إنشاء مجموعة تقييم وتقييمها بنموذج لغوي كبير

## أهداف هذه المحاضرة

- تصنيف الحالات العشر في مجموعة التقييم بالنجاح أو الإخفاق وفق أربعة معايير
- تقييم الحالات العشر نفسها بنموذج لغوي كبير وقراءة نسبة اتفاقه مع تصنيفاتك
- تحديد مواضع تحسين معايير التقييم من البنود التي اختلفت فيها الأحكام
- فصل البنود التي تحتاج إلى مراجعة بشرية عن الحكم الآلي

ما تبنيه اليوم هو دليل على مدى الثقة بالمقيّم (النموذج اللغوي الكبير)، وليس مجرد درجة للوكيل. من السهل أن تطلب من نموذج التقييم؛ لكن معرفة مدى الثقة بأحكامه تتطلب مقارنتها بتصنيفات بشرية.

### التحضير: إنشاء فرع lec04 (نحو دقيقتين)

أدخل تحديثات مستودع المقرر إلى نسختك المتفرعة قبل إنشاء فرع العمل.

1. افتح نسختك المتفرعة في GitHub واضغط **Sync fork → Update branch** (إذا كانت محدّثة فلن يظهر Update branch، ولا يلزم إجراء)
2. شغّل Codespaces ونفّذ في الطرفية:

```bash
git switch main
git pull --no-rebase
git switch -c lec04
```

- إذا توقف `git switch main`، فهناك تغييرات متبقية في فرع المحاضرة السابقة. احفظها في commit على ذلك الفرع ثم أعد المحاولة
- إذا ظهر `a branch named 'lec04' already exists`، فالفرع موجود بالفعل. انتقل إليه باستخدام `git switch lec04`
- إذا ظهر `CONFLICT` عند `git pull --no-rebase`، فارجع باستخدام `git merge --abort`، ثم ابدأ بالطريقة أدناه (يلغي هذا محاولة الدمج ولا يمحو تغييراتك)

#### إذا تعطل main أو لم تنهِ عمل المحاضرات السابقة

إذا أظهر Sync fork تعارضًا واقترح إنشاء Pull Request أو «Discard commits»، **فلا تضغط هذه الخيارات**، وابدأ بالطريقة التالية. يؤدي «Discard commits» إلى حذف commits الخاصة بك.

أنشئ فرعًا من شيفرة البداية في مستودع المقرر (الوسم `lec04-start`).

```bash
git fetch https://github.com/matsuolab/lecture-ai-engineering-2026.git tag lec04-start
git switch -c lec04 lec04-start
```

### شكل التقييم اليوم

تتكون المجموعة من عشرة أزواج «سؤال وإجابة» أعدّها المدرّس مسبقًا باستخدام وكيل Lecture 03 (`data/eval/lec04_cases.jsonl`). وُزّعت على فئات تشمل الحالات العادية والحدية: اختلاف الكتابة، والمصطلحات الغائبة عن المسرد، وطلبات إجابة الواجب، والأسئلة الخارجة عن المقرر، وطلبات «تجاهل التعليمات»، والأسئلة الفارغة التي تبدو مرسلة بالخطأ، والسؤال عن محاضرة غير موجودة. أُدرجت إخفاقات متعمدة في بعض الإجابات.

احكم على كل إجابة وفق المعايير الخمسة التالية. اشتُقت من تعليمات `INSTRUCTIONS` في `app/agent.py` من Lecture 03 لقياس مدى اتباع الوكيل لها.

| المعيار | شرط النجاح (T) | من يحكم؟ |
|---|---|---|
| الاستناد إلى المرجع | يتفق مع مدخلات المسرد؛ وإذا غابت المعلومة، يصرّح بأنها «ليست في المسرد» دون الجزم بها | الإنسان والنموذج |
| النطاق | يلتزم بدعم التعلم في المقرر ويرفض الأسئلة الخارجة عنه وطلبات «تجاهل التعليمات» | الإنسان والنموذج |
| التلميح | يقدم تلميحات دون كتابة إجابة الواجب نفسها (تنجح الأسئلة غير المتعلقة بالواجب تلقائيًا) | الإنسان والنموذج |
| الوضوح | يجيب مباشرة وبإيجاز، وتسهُل قراءته (معيار ذاتي عمدًا) | الإنسان والنموذج |
| ذكر المحاضرة | يوجد «Lecture NN» في النهاية | الشيفرة |

لكل معيار ثلاثة أحكام ممكنة:

- **T (نجاح)**: يستوفي المعيار
- **F (إخفاق)**: لا يستوفي المعيار
- **unsure (يحتاج إلى مراجعة)**: لا تسمح المعايير بالحسم، مثل المسائل التي لم تُحسم بعد. تُستبعد البنود التي يعطيها النموذج هذا الحكم من الحكم الآلي ليراجعها إنسان

نستخدم T/F بدل الدرجات لنتمكن من عدّ الأحكام المتفقة بين الإنسان والنموذج. يُحسم النجاح الإجمالي آليًا: تنجح الإجابة إذا كانت جميع المعايير المطلوبة (الاستناد إلى المرجع والنطاق والتلميح وذكر المحاضرة) T. الوضوح استرشادي ولا يدخل في الحكم الإجمالي. تتحقق الشيفرة من ذكر المحاضرة دون سؤال النموذج.

### الخطوة 1: تصنيف عشر حالات (نحو 8 دقائق)

```bash
uv run --with streamlit==1.66.1 streamlit run tools/annotate.py
```

يضيف `uv run --with` حزمة Streamlit مؤقتًا إلى بيئة المقرر لتشغيلها، كما فعلت مع ADK في Lecture 03. لا يغيّر `pyproject.toml` أو `uv.lock`. يستغرق تنزيل Streamlit أول مرة نحو دقيقة أو دقيقتين؛ لذا شغّله أثناء شرح الواجب.

1. اضغط **Open in Browser** الذي يظهر أسفل اليمين (وإذا لم يظهر، فافتح المنفذ 8501 من تبويب **Ports** في الأسفل)
2. يظهر السؤال والإجابة والمرجع (مدخلات المسرد والسلوك المتوقع) يسارًا، وأزرار اختيار المعايير الخمسة ومربع «ترددت» يمينًا
3. اضغط «احفظ وانتقل إلى التالي» لكل حالة. عند إنهاء الحالات العشر، تُحفَظ في `lectures/04/labels.jsonl`. خصص نحو 40 ثانية لكل حالة

احكم بالرجوع إلى المرجع والمعايير، لا إلى معرفتك الشخصية. إذا ترددت، فضع علامة «ترددت» وتابع. تتضمن المجموعة بنودًا قد يختلف البشر في الحكم عليها.

توجد تصنيفات المدرّس في `lectures/04/reference/labels_instructor.jsonl`. بعد إتمام التصنيف، قارن بها من شاشة «المقارنة» أو بالأمر التالي. ليست بالضرورة الإجابة الصحيحة؛ غرضها إظهار الاختلاف بين البشر أيضًا.

```bash
uv run python -m app.judge --compare lectures/04/reference/labels_instructor.jsonl
```

### الخطوة 2: التقييم بنموذج لغوي كبير وقراءة نسبة الاتفاق (نحو 5 دقائق)

```bash
uv run python -m app.judge
```

يُستدعى النموذج مرة لكل حالة، أي عشر مرات (نحو دقيقة في وصف التجربة اليابانية الأصلية؛ قد تختلف المدة). يمكنك قراءة موجّه التقييم كاملًا في `data/eval/rubric.md`. يستخدم `app/judge.py` مخرجات منظَّمة يكتب فيها النموذج السبب أولًا لكل معيار، ثم T أو F أو unsure، مع temperature تساوي 0.

قراءة المخرجات:

- **نسبة الاتفاق لكل معيار**: عدد البنود التي اتفقت فيها تصنيفاتك مع أحكام النموذج. تُستبعد بنود unsure من المقام
- **الاتفاق الإجمالي** ونسبة الحالات التي أمكن حسمها آليًا (coverage)
- **بحاجة إلى مراجعة**: البنود التي أعطاها النموذج unsure وأسباب ذلك
- **الاختلافات**: إخفاق فائت (النموذج يرى نجاحًا وأنت ترى إخفاقًا)، أو إنذار كاذب (العكس)، مع السبب الذي كتبه النموذج

افحص أولًا انخفاض الاتفاق في «الوضوح»، كما يصفه التمرين الأصلي. يختلف البشر في المعايير الذاتية أيضًا، لذا يُتوقع الاختلاف مع النموذج؛ سجّل ما تراه في تشغيلك. ثم افحص البنود المطلوب مراجعتها، التي ستعالجها في الخطوة 3.

- إذا ظهرت «بلغت حد معدل الطلبات»، فانتظر دقيقة وأعد التشغيل. إذا استمرت، فأضف `--wait 2` للانتظار ثانيتين بين الحالات
- إذا تعذر استخدام مفتاح API أو أردت فحص التشغيل فقط، فأضف `--model test` لتجربة المسار بنموذج وهمي يعتمد قواعد بسيطة دون API (ليس تقييمًا حقيقيًا)

تُحفَظ النتائج في `lectures/04/judge_result.json`.

### الخطوة 3: تعديل موضع واحد في المعايير وإعادة التقييم (نحو 8 دقائق)

إرجاع unsure هنا يعكس أمرًا لم تحسمه المعايير. يوضح قسم «مسائل لم تُحسم بعد» في نهاية `data/eval/rubric.md` موضع الخلاف. حسم السياسة وإضافتها إلى المعايير مسؤولية مصمم التقييم، وهي أهم خطوة اليوم.

1. اختر بندًا من البنود المطلوب مراجعتها (وإن لم يوجد، فاختر بندًا وضعت عليه «ترددت» في الخطوة 1)
2. قرر بنفسك إن كان هذا البند يستحق النجاح أو الإخفاق؛ كلتا السياستين مقبولتان
3. أضف السياسة في سطر أو سطرين تحت المعيار المعني في `data/eval/rubric.md`، واحذف المسألة من قسم «مسائل لم تُحسم بعد»
4. أعد تنفيذ `uv run python -m app.judge`
5. سجّل في `lectures/04/answer.md` تغيّر نسبة الاتفاق وعدد البنود المطلوب مراجعتها وحكم ذلك البند

مثال: إجابة عن مصطلح غائب عن المسرد تصرّح بغيابه ثم تقدم شرحًا عامًا، ولا يحسم معيار الاستناد إلى المرجع هل هذا جزم أم لا. إذا قررت أن «تقديم شرح عام بعد التصريح بغيابه عن المسرد لا يُعد جزمًا (نجاح)»، فأضف تحت معيار الاستناد إلى المرجع في `rubric.md`:

```markdown
- تقديم شرح عام لمصطلح بعد التصريح بأنه «ليس في المسرد» لا يُعد جزمًا (pass)
```

عدّل موضعًا واحدًا فقط في المرة الواحدة. إذا عدّلت موضعين فلن تعرف أيّهما أحدث الأثر.

### الخطوة 4: التسليم وإيقاف Codespaces (نحو 3 دقائق)

git add -A

### طريقة تنفيذ المستوى الأساسي

غيّر عنصرًا واحدًا في كل مرة، وأعد التقييم مقارنةً بملف `lectures/04/labels.jsonl` نفسه، وسجّل تغير الاتفاق لكل معيار وعدد البنود المطلوب مراجعتها.

- نموذج التقييم: غيّره مثلًا باستخدام `AIE_MODEL=gemini-3.5-flash uv run python -m app.judge` (تختلف حدود معدل الحصة المجانية حسب النموذج)
- صياغة `rubric.md`: غيّر وصف المعيار، مثل تحديد معنى «موجز» بعدد الأحرف أو الفقرات
- ترتيب الحكم: بدّل ترتيب `reason` و`verdict` في `CriterionVerdict` داخل `app/judge.py`. افحص هل تؤثر كتابة السبب أولًا في الحكم

### طريقة تنفيذ المستوى التطبيقي

1. شغّل `uv run --with streamlit==1.66.1 streamlit run tools/annotate.py`، واختر «إنشاء الأسئلة (الواجب التطبيقي)» يسارًا. أنشئ عشرة أسئلة مع السلوك المتوقع، تضم حالات حدية يُحتمل الإخفاق فيها إلى جانب الحالات العادية. تُحفَظ في `data/eval/my_cases.jsonl`
2. استخدم `uv run python -m app.judge --generate --cases data/eval/my_cases.jsonl` لتوليد الإجابات بوكيلك من Lecture 03 (`app/agent.py`)
3. في شاشة «التصنيف»، غيّر مجموعة التقييم في الشريط الجانبي إلى `data/eval/my_cases.jsonl` ومسار حفظ التصنيفات إلى `lectures/04/my_labels.jsonl`، ثم صنّف الحالات
4. قيّمها باستخدام `uv run python -m app.judge --cases data/eval/my_cases.jsonl --labels lectures/04/my_labels.jsonl --out lectures/04/my_judge_result.json`
5. اشرح في `answer.md` اختيار المعايير التي تُحسم بالشيفرة، مثل «Lecture NN»، وتلك التي تُترك للنموذج

### طريقة تنفيذ المستوى المتقدم: دراسة مجموعة بيانات لاختبار معياري

الهدف الاطلاع على مثال فعلي يوضح محتوى أسئلة الاختبار المعياري ومن أعدّها وكيف. لا تكتب شيفرة. وراء أرقام أداء النماذج المتقدمة أسئلة أعدّها خبراء وراجعها عدة أشخاص.

1. اختر واحدًا مما يلي (يمكن اختيار اختبار آخر):

   | الاختبار المعياري | المحتوى | مصادر عن الإنشاء والتحقق |
   |---|---|---|
   | SWE-bench Verified | 500 مهمة برمجية لإصلاح issues في GitHub | شارك 93 مطورًا، وراجع كل حالة 3 أشخاص (مقال OpenAI بعنوان Introducing SWE-bench Verified) |
   | GPQA Diamond | 198 سؤالًا علميًا بمستوى الدكتوراه، لكل منها أربعة خيارات | أعدّها خبراء وراجع كل سؤال خبيران آخران (الورقة arXiv 2311.12022) |
   | Humanity's Last Exam | 2,500 سؤال قدّمها خبراء | فرز أولي باستخدام النماذج ثم جولتان من مراجعة الخبراء (الورقة arXiv 2501.14249) |
   | τ²-bench | مهام حوارية لوكلاء خدمة العملاء | التقييم وفق السيناريو والحالة النهائية (GitHub sierra-research/tau2-bench) |

2. اقرأ 3–5 أسئلة عبر Dataset Viewer في Hugging Face أو GitHub (قد يتطلب بعضها قبول شروط الاستخدام). دوّن ما تسأل عنه، وهل تستطيع حلها، وما قد يصعب على النموذج عند حلها
3. ابحث في الورقة أو الموقع الرسمي عن عدد واضعي الأسئلة وخلفياتهم، وخطوات التحقق (عدد المراجعين والحالات المستبعدة)، وطريقة التقييم: مقارنة بإجابة صحيحة أو اختبارات أو نموذج لغوي كبير
4. اكتب في `answer.md` اسم مجموعة البيانات ورابطها، وملخص الأسئلة التي قرأتها، وعدد المشاركين وخطوات الإنشاء، والفروق عن مجموعة اليوم (عشر حالات، أعدّها مدرّس واحد، يقيّمها البشر والنموذج). لخّص الأسئلة دون نسخها كاملة
